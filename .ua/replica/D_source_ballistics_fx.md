# D 飞羽青春源码与回放层面的弹道、能量、动作、特效、相机事实

日期：2026-11-27。作者：任务 D 子代理。只读资料：`References/fyqc/fyqc-client/`。
证据标注：[源码事实] 带 `文件:行号`；[配置事实] 指 `text/*.txt` 里的原始字段；[回放实测] 指从 `replays/*.replay` 逐帧解码得到的数；[回放拟合] 指用回放数据拟合出的模型；[推测] 是我的推断。
长度单位：逻辑层是厘米（cm），配置表多为米（m）。逻辑帧 25 帧/s（1 帧 = 0.04 s）。坐标：X 左右，Y 高度，Z 前后，网在 Z=0。

## 0 一页结论

1. 屏幕底部的条就是“能量”，逻辑层名字叫 COUNTER_TYPE_CONTINUOUS（连击计数器），范围 0–100。基础规则 [回放实测]：内圈击球（弹“完美”）+20；中圈跨步击球不变；外圈救球或鱼跃（弹“糟糕”）−40，最低 0；每个回合结束清零；双打默认全队共用一条。
2. 能量影响球的唯一途径是“换曲线 ID”。每个普通球路都有 _0、_1、_2 三条连号曲线，击球瞬间按能量选：能量 <40 用 _0，40–99 用 _1，100 用 _2。速度倍率属性（P/D/GY_BADMINTON_SPEED_MUL）在 9 个回放里从头到尾都是 10000，没有被能量改过。
3. 三档的实际差别 [回放拟合后的同条件计算]：飞行时间缩短到 _0 的 0.83–0.90 倍（中档）和 0.50–0.77 倍（满档）。弧线被压低只发生在“远球”（平远族）并且击球点高于约 160 cm 时：出球角从 5° 或 10° 变成 0°，顶点降 27–88 cm，而且到 40 点能量就已经压平。近球和高球三档的轨迹形状完全一样，只是放得更快。用户说的“能量越高球越快”全对，“弧线被压低”只对远球成立。
4. 普通球（NORMAL 族）的弹道数学已经复原并用 425 条回放轨迹验证，位置误差中位数 2.2 cm：二次阻力抛体（k=0.24 /m，g=5.0 m/s²）定形状，出球角取配置值并按 5° 一档抬到刚好过网，初速反解到落点，再做一次“时间重映射”决定快慢。扣杀类（PARABOLA 族）是精确抛物线加匀速。可直接用的实现在 `.ua/replica/tools/D_fy_curve.py`。
5. 动作由“按键 × 球到人的水平距离（三圈）× 击球高度 × 8 方向”选出，击球质量完全由圈层决定。三圈半径基础值 90 / 150 / 250 cm，移速 380（前、左、右）/ 310（后）cm/s，无加速段。
6. 特效 prefab 一个都没导出。能看到的只有粒子贴图、UI 精灵、OBJ 网格、编译后的 shader 和材质二进制，以及配置表里的 prefab 路径和参数。可以当“飞羽有哪些特效位”的清单用，不能直接拿来用。

### 1.3 回放怎么用

回放文件是 `Common_pb2.ReplayDataMsg`（`python_src/base/protobufdata/Common_pb2.py:5621-5718`），每帧一组服务器下发消息，每条 = 1 字节 0xa1 + 1 字节消息号 + 4 字节对象 ID + protobuf 体。消息号与类的对应见 `python_src/prediction/nethandler.py:456-494`。用到的消息：

| 消息 | 号 | 内容 |
|---|---|---|
| BATTLE_POS_MSG | 6 | 球每帧的 X、Y、Z（cm）；球员每帧 X、Z |
| BATTLE_HIT_RES_MSG | 3 | 击球者用的动作 ID、按键、HitType |
| BATTLE_BADMINTON_CURVE_MSG | 63 | 起点、落点、曲线 ID、速度倍率、出球方向、是否发球 |
| BATTLE_UPDATE_COUNTER_MSG | 57 | 计数器当前值（只发给本人，所以只有录制者的能量） |
| BATTLE_PROP_CHANGE_MSG | 41 | 属性值（移速、三圈半径、速度倍率等） |
| BATTLE_BADMINTON_STAR_MARK_MSG | 26 | 星标位置 |

9 个回放都是房间双打、带技能，共 2179 次击球，其中录制者本人 318 次带能量值。局限：没有单打和经典模式样本；技能会额外加减能量（每秒 +5、被对手每秒 −2 等），基础规则是从“没有技能干扰的那几下”里读出来的。

脚本都在 `.ua/replica/tools/D_*.py`，数据在 `.ua/replica/data/D_*`，清单见 §13。

### 2.2 NORMAL 族（1000–1031）的数学形式

原生层的做法（`curve_reimpl/原生层反编译-phys模块解密.md`）是查一张预制剖面表 g_CurveData：按“起点高度 10–260 cm 每 10 cm 一档 × 出球角 −30°–80° 每 5° 一档”存了 553 条剖面，每条是按 0.016 s 采样的点表。这张表本机没有全点，但回放证明它就是下面这个物理模型的采样结果，所以可以直接用公式代替查表。

[回放拟合] 模型分三步。

第一步，形状。二维竖直面内的二次阻力抛体：

```
加速度 = −k·|v|·v − g·ŷ
k = 0.24 /m，g = 5.0 m/s²，模型步长 0.016 s
```

这三个数就是 `text/curveconstant.txt` 1000 组的 airFriction 0.24、gravity −5.0、timeGap 0.016。只按形状拟合回放轨迹时残差 0.2 cm，拟合出的出球角全部落在 5° 的整数倍上，和剖面表的角度网格一致。

第二步，出球角和初速。

```
角度 = 曲线配置的 angle
如果球路跨网，且用这个角度打到落点时网处高度 < 约 157 cm：
    角度 += 5°，重算，直到过网
初速 v0 = 让球恰好落到落点的那个值（二分反解）
```

过网阈值 [回放实测]：通过的最低过网高度 156.2–157.1 cm，被拒绝的最高 157.6 cm。配置里 netHeight 1.5 m + netFixH 0.08 m = 158 cm，吻合。后果很重要：近网低手位击球会被自动抬成高弧。例如高球 1003 配置 25°，从 49 cm 高度、网在路径 11% 处打出时变成 55°，顶点 676 cm；近球 1000 配置 10°，从 49 cm 打出时是 35–40°。

第三步，时间重映射。形状定了以后，球沿这条形状走的快慢不是物理时间，而是每个 0.016 s 的模型步被赋予一个“真实耗时”：

```
tMin = 模型弹道上速率最小的时刻（一般在顶点之后；平直球没有极小值就取落地时刻）
t0s  = (1 − speedLerpFactor/100) × tMin
模型时间 tau < t0s          ：每步真实耗时 = firstHalfSegmentTime 毫秒
t0s ≤ tau < tMin            ：从 first 线性过渡到 last
tau ≥ tMin                  ：每步真实耗时 = lastHalfSegmentTime 毫秒
最后全部除以 速度倍率 iSpeedMul
```

也就是：真实速度 = 模型速度 × 16 / seg × 速度倍率。first 小于 16 表示前段比物理弹道快放，last 大于 16 表示后段慢放。例：高球 1003（first 8、last 20）前段 2 倍速冲上去，过顶点后以 0.8 倍速慢慢落；远球 1013（12、24）前段 1.33 倍速，后段 0.67 倍速。飞羽“出手很冲、末段飘落”的手感主要来自这一步，加上二次阻力本身的强减速。

曲线时间起点 [回放拟合]：位置帧 f 对应曲线时间 (f − 击球帧) × 0.04 + t0，t0 中位 0.065–0.080 s。和 `defines.py:20` 的 CURVE_WAIT_TIME 0.08、`badminton.py:226` 的 AddPassTime(0.04) 对得上。意思是击球那一帧球已经离拍飞了约 2 帧的量。

验证 [回放拟合]：`D_model_validate.py` 对 26 个曲线 ID 共 425 条轨迹做前向计算，位置平均误差中位数 2.23 cm，90 分位 4.32 cm。

| 项 | 等级 |

### 2.3 PARABOLA_DOWN 族（4000–4014）

[回放拟合] 形状是精确抛物线，残差 0.0 cm：

```
y = y0 + b·s − a·s²      （s 是水平距离，单位 cm）
a 的默认值 = parabolaMaxA × 1e-6 /cm（最弯）
如果网处高度不够：减小 a，直到网处高度恰为 155.0 cm
a 的下限 = parabolaMinA × 1e-6 /cm（最直）
b 由“落到落点”反解
```

速度沿弧长近似匀速：velocity（cm/s）× 速度倍率。总时长 ≈ 起点到落点的弦长 / velocity / 速度倍率（弧长与弦长差不到 1%）。没有阻力，也没有时间重映射，所以扣杀的观感是一条直冲到底的线。

实测：4006 / 4007 / 4008 的速度 10.5 / 11.8 / 13.8 m/s（即 1000 / 1150 / 1300 cm/s × 1.05 的被动加成）；星标扣球 4003 速度 16.8 m/s，起点恒为 400 cm 高，距离 981–1248 cm，过网高 212–250 cm，全程 0.63–0.74 s。

### 2.5 落点

[源码事实] `badminton.py:425-516`，[配置事实] `text/curvedrop.txt`。

```
fRand = 0–1 随机数
fOffset = fRand ^ ((100 − 聚拢值) / 100)          聚拢值 = 属性 DROPPOS_GATHER/100，基础 40，指数 0.6
近球键的前后向：fGood = Std − Std×Off，fBad = Std
其他情况：      fGood = Std + (1−Std)×Off，fBad = Std
比例 = (fGood − fBad) × fOffset + fBad
前后：落点到网的距离 = 比例 × 半场长 670 cm        远球、高球用 far 组，近球用 near 组
左右：落点 |X| = 比例 × 半场宽（单打 260，双打 305 cm）
无方向时：X 比例在 ±(1 − 比例) 内随机              也就是落在中路
有方向时：落点 X 不越过起点 X 的另一侧
```

fRand 越大越靠 fGood（更刁钻），聚拢值越高越容易靠 fGood。状态脚本可以直接改聚拢值和偏移（`python_src/battlelogic/plugins/state/statefunc.py:130-145`），属性 DROPPOS_LEFT/RIGHT/NEAR/FAR_OFFSET 基础值都是 0。

## 4 能量、连击、星标系统与对弹道的影响

### 4.1 那根条是什么

[源码事实] 能量就是 COUNTER_TYPE_CONTINUOUS=1（`python_src/base/protobufdata/BattleCmd_pb2.py:2627-2635`）。证据链：
- 结算数据把 BATTLE_RECORD_HIGH/MIDDLE/LOW_CONTINUOUS 记成 highener / midener / lowener（`python_src/battlelogic/sceneplugins/battlereport/bigdata.py:145-147`）。
- AI 读取 `GetCounterValue(COUNTER_TYPE_CONTINUOUS)` 存成 "er"（`python_src/battlelogic/sceneplugins/gameai/gameai.py:139`）。
- 结算界面文案是“平均能量、高能量击球、中能量击球、低能量击球、完美球数”（`text/commonmultilingualsimplifiedchinese.txt` L2700-2712），和 `python_src/battlelogic/gameplayer.py:616-629` 的 High / Middle / Low / AVG ContinuousTimes 一一对应。
- DLL 里 HUD 元素名单是“摇杆 近球 远球 高远球 主动 道具 表情 能量条”，特效触发键里有“第一次满能量、第二次满能量、三次及以上满能量”（`text/Game_dll.txt` L85641、L85812）。

所以旧研究里看到的“连击条 GUI_ComboBar”和“能量条”是同一个东西：美术资源叫 ComboBar，逻辑叫 Continuous，对玩家叫能量。FlyText 的 ComboUp / ComboDown / ComboMax 是能量升档、掉档、满档的飘字。

计数器一共 8 种（同上枚举）：CONTINUOUS=1 能量，STARMARK=2 星标，RETRIEVE_SMASH=3，BAD_CURVE=4，SKILL_1=5，BOT_WATER=6，CONTINUOUS_PERFECT=7，HITNUM=8。

### 4.2 数值怎么涨怎么掉

计数器容器 [源码事实] `python_src/battlelogic/plugins/counter/countermanager.py:11-122`：值夹在 [0, maxvalue]（:26-36）；每次变化发事件并通知客户端（:38-54，`python_src/battlelogic/combatobjectdynamic.py:585-617`）；得分时把标了 isscoreclear 的计数器清零（:98-107）；双打时如果场景开了 m_TestShareContinuous，能量变化同步给队友（`combatobjectdynamic.py:599`、`:608`；默认开，`python_src/battlelogic/scene.py:77`）。

Python 核心代码不直接加减能量。加减是由一个挂在球员身上的状态“5000 通常击球能量-监听击球”（`text/state.txt`）监听击球事件后，调用脚本函数 StateSetCounterValue 完成的（`python_src/battlelogic/plugins/state/statefunc.py:126-127`）。这个状态的脚本本机没有，下面的数来自回放。

基础规则 [回放实测]：

| 事件 | 能量变化 | 依据 |
|---|---|---|
| 内圈动作 2001–2008 击球（弹“完美”） | +20 | 9 回放共 274 次 +20 |
| 中圈跨步动作 3001–3008、4001–4008 击球 | 0 | 逐次对照无变化 |
| 外圈救球、鱼跃 5001–5028 击球（弹“糟糕”） | −40，最低 0 | 41 次 −40，另有 40→0、20→0、30→0 |
| 上限 | 100 | 85→100 被夹住；文案“能量上限为100点” |
| 回合结束 | 清零 | 每次比分变化时带发球标志归 0 |
| 双打 | 全队共用 | 队友击球会改变录制者的能量值 |

五下完美从 0 到满。每个回合都从 0 开始，所以长回合后段球才会快起来。

技能和模式带来的额外变化（不属于基础规则）：
- 经典模式 [配置事实] `text/prefablanguagesimplifiedchinese.txt` L4648、L4660：“局内能量可自动回复，回复速率为每秒5点；击球为完美球时回复20点能量，击出糟糕球不再扣除能量，能量上限为100点。” 这句话同时旁证了普通模式的完美 +20。
- 回放里见到的技能效果：每秒 +5（“能量每秒增加 5 点”类技能）、每 25 帧 −2（对手的能量窃取）、完美 +30（疑为“强化能量”）。
- `text/skill.txt`：逆境选手以 40 点和 80 点为阈值；能量震波、冰冻球按低 / 中 / 高（满）三档给效果；狂热步法在能量满时加移速 30% 起；反客为主完美回击扣球 +55 点。
- 道具“完美主义”（`text/propertybox.txt` L27）：下一次普通击球若完美则充满，若救球则清空。

### 4.3 能量通过什么途径影响击球

[回放实测] 途径只有一条：选曲线。

排除项：整场对局里 P / D / GY_BADMINTON_SPEED_MUL 三个属性始终是 10000，没有任何一次变化。HIT_BADMINTON_AVERAGE_SPEED_MUL 只出现过 10000、10500（开局就加上，是被动技能的 +5%）和 14100（某技能状态期间）。所以旧研究盯着的 `badminton.py:259-263` 那条 iSpeedMul 链路是给技能和属性用的，不是能量用的。

### 4.5 星标（紫色光圈那套）

星标是另一个计数器 COUNTER_TYPE_STARMARK，和能量无关，方向是惩罚打得差的一方。

[源码事实] 出球后检查 `badminton.py:398-405`：如果这条曲线能算出星标位置（CalcStarMarkPos 非零），并且击球者的星标计数 ≥ maxvalue（`:562-572`），就在球路上亮出星标。对手站进星标半径内，且球预判高度 > 270 cm（`defines.py:66`）时，他这一拍的 HitType 变成 STARMARK（`python_src/battlelogic/combatobjectdynamic.py:383-392`，`dohitaction.py:456-465`），动作变成 1076 星标扣球。星标半径是属性 STAR_MARK_RADIUS，基础 100 cm。

[回放实测]：
- 星标计数在本人外圈击球（5xxx 动作）时 +1（0→1 共 39 次，1→2 共 11 次），最大值 2；本人下一次内圈或中圈击球、或者回合结束时清零。
- 计数到 2 的那一拍，不管按的是近球、远球还是高球，出的都是 1022“触发星标的球路”（67 次，全部来自 5xxx 动作）：一个 25° 起步、落点只去后场（dropId 1005，到网 568–640 cm）的慢高球，拖尾是 TW_trail_bad。
- 星标位置只在 1022 这条曲线上出现（65 次），是地面上的一个点，位于路径的 58%–96%（中位 87%）处。
- 对手打 1076：原地起跳 4.0 m、蓄势 1.2 s、击球点恒在 400 cm 高，出 4003（1600 cm/s，全场最快的球）。

翻成人话：连续两次靠救球把球捞回去，第二次捞出来的就是一个送给对手的后场高球，对手站到光圈里就能来一记全力扣杀。接星标扣球的那方还会被挂“击退 200 / 350 / 500”之类的状态（`text/state.txt` 8001–8003），具体数值在缺失的脚本里。

另一个“紫色光圈”是普通跳扣：提示文案“当球在空中闪烁紫色光圈时按下近球/远球键，可触发球速较快的跳扣”（`text/languagetextsimplifiedchinese.txt` tips_content_1013），对应状态 5016–5018“跳扣高度检测”和动作 2009，见 §6。

其他计数器 [回放实测]：BAD_CURVE 在本人外圈击球时置 1，对手回击后清零；RETRIEVE_SMASH 在救回对手扣杀时置 1；HITNUM 每次击球 +1。CONTINUOUS_PERFECT=7 在回放里没有出现过更新消息，用途未知。

### 4.6 属性与状态的数据流

- 属性公式 [源码事实] `python_src/battlelogic/plugins/prop/propcontainer.py:48-97`：值 = (初值 + 所有加值) × (10000 + 所有万分比) // 10000，再夹上下限，变化时通知客户端。
- 状态改属性的唯一入口 `statefunc.py:18-21` StateChangePropValue。状态还能加减别的状态、设计数器、改落点聚拢和偏移、强制动作、设子弹时间（`statefunc.py:31-170`）。
- 状态脚本能读的条件：属性值、当前击球动作的类型（内圈 / 跨步 / 救球）、计数器值、到球的水平和垂直距离、按键、到网距离、曲线总时长等（`python_src/battlelogic/plugins/state/statevalue.py:20-280`）。所以“内圈击球加 20 能量”这种规则写成状态脚本是很自然的。
- 数值表：属性初值随建局消息下发（回放第 0 帧可读，见 §7）；状态名单在 `text/state.txt`（508 条，只有名字和子状态表）；技能描述和数值在 `text/skill.txt`；状态和动作挂的特效在 `text/StateEffect.txt`、`text/hitactioneffect.txt`。

## 5 击球质量

质量不是单独算的，它就是“这一拍用了哪一圈的动作”。

[源码事实] 三圈判定 `combatobjectdynamic.py:394-437`：球到人的水平距离 < HIT_RADIUS 是内圈；在 HIT_RADIUS 和 STRIDE_RADIUS 之间是中圈（跨步）；在 STRIDE_RADIUS 和 RETRIEVE_RADIUS 之间是外圈（救球）。半径按球相对人的 8 个方向各有一个属性（`defines.py:90-115`）。AI 侧的命名：INSIDE→1，MIDDLE→2，OUTSIDE→3（`python_src/battlelogic/sceneplugins/gameai/gameairerun.py:64-74`）。

| 圈 | 半径基础值 [回放实测] | 动作 | 弹字 [配置事实] `text/hitactioneffect.txt` effectType 15 | 能量 | 星标计数 |
|---|---|---|---|---|---|
| 内圈 INSIDE | 0–90 cm（8 向相同） | 2001–2008，起跳 2009 | quality 0，“完美”（GUI_Hitgood） | +20 | 清零 |
| 中圈 MIDDLE | 90–150 cm（技能可到 160–164） | 跨步 3001–3008、4001–4008 | quality 1，普通 | 0 | 清零 |
| 外圈 OUTSIDE | 150–250 cm | 救球 5001–5018 | quality 2，“糟糕”（GUI_Hitbad） | −40 | +1 |
| 圈外鱼跃 | 按键时距离 271–339 cm（中位），最远约 390 cm | 鱼跃 5021–5028 | quality 2 | −40 | +1 |

服务器判定时每圈有 15 cm 容差（`defines.py:42`，`combatobjectdynamic.py:377-381`）。

不同圈层出的球有什么差别：
- 曲线不同：近球键内 / 中 / 外圈分别出 1000 族 / 1006 族 / 1009 族，远球键出 1013 族 / 1016 族 / 1019 族，高球键三圈都出 1003 族。
- 速度：同条件下三圈的总时长只差 0–10%（见 §4.4 的近球三行）。圈层对球速的直接影响很小，真正的差别来自能量：内圈攒能量，外圈掉能量。
- 弧线：低能量时，远球外圈的出球角是 10°，比内圈和中圈的 5° 高，球更飘。近球内圈配置 10°，中圈和外圈 0°，但近球几乎总被过网规则抬高，实际看不出差别。
- 落点精度：三圈用的是同一张落点表 1002，源码里没有“外圈落点更散”的机制。
- 后摇：内圈可移动后摇 0.08 s，中圈 0.38 s，外圈 0.76 s（§7.3）。打得越勉强，越久不能动。这是圈层最大的代价。

场区（前场、中场、后场）不参与选动作，也不参与选曲线。回放里同一个键在前场和后场出的曲线 ID 是一样的。场区的影响是间接的：
- 离网近、击球点低，出球角会被过网规则抬高，近球变成小高弧，高球变成 45–65° 的大高弧。
- 离网远、击球点高，远球才能打出 0° 的平直球。
- 落点由落点表决定，和击球者站在哪里无关（只有“带方向时落点 X 不越过起点 X”这一条关联）。

所以飞羽里没有“搓、推、挑、吊、杀”这些按场区自动切换的球种。普通球只有三个键 × 三圈 × 三档能量 = 21 条曲线（高球三圈共用），外加跳扣三档、星标扣球、星标球路和发球两条。更细的球种（勾对角、劈吊、平抽、扑球等）都是技能。

### 7.2 击球时的移动锁定和自动位移

- 锁定 [源码事实] `combatobjectdynamic.py:337-347`：动作不允许移动施放时，从按键起到“前摇 + 挥拍 + 可移动后摇”结束之前不能走。救球、鱼跃、扑球圈是“可移动击球”（isMovableHit），不走这条。
- 自动位移 [源码事实] `dohitaction.py:416-454`：动作配置给出一段位移（水平量、垂直量、时间），方向指向球的预判位置，动作期间角色切到自动移动沿这条路径走。这就是跨步、鱼跃、起跳。

- 朝向 [源码事实] `dohitaction.py:322-327`：击球朝向 = 球在“前摇帧 + 挥拍帧 / 3”时的预判位置减人的位置。

### 8.2 球与网、地面、出界

- 过网：出球时曲线生成阶段就做了过网修正（§2.2、§2.3），所以正常击球不会撞网。撞网只发生在不做过网修正的曲线（1029、4010）或起点太贴网时。原生层检测到撞网后回调 `scene.py:156-164`，标记球已被击中、发撞网事件和撞网消息。客户端预判：球到网平面时 Y ≤ 网高就判撞网（`python_src/clientlogic/prejudgecurve.py:55-65`）。
- 落地：曲线走完即落地，回合结束（`badminton.py:364-369`）。
- 判分 [源码事实] `badminton.py:351-359`：球打到人，打到谁谁的对方得分；否则看落点是否在对方的得分区内（`scene.py:817-825`，按单打 / 双打、是否发球取不同的矩形），在界内击球方得分，出界对方得分。
- 出界：落点表的范围都在界内，正常击球不会出界。出界要靠专门的曲线（4009 跳扣出界）或属性偏移。
- 打到人：球碰到人的碰撞体算身体击中（`badminton.py:180-189`、`:371-376`），有专门的飘字 BodyShot。
- 球不能连击：只有球在击球者自己半场、处于自由飞行、且没有被预判击中时才能打（`badminton.py:197-219`，`dohitaction.py:467-483`）。双打里有“锁定者”机制，锁定后只有那个人能打。
- 子弹时间：`python_src/battlelogic/plugins/bullettime/bullettimemanager.py:32-45`，状态脚本可以给人、球、全场设时间缩放（`statefunc.py:112-117`）。星标扣球有专门的子弹时间状态 1030。

### 10.2 能推出的结构

[推测，依据 DLL 字符串] 主相机是 Cinemachine 虚拟相机 Camera/MainVCam，挂在一条轨道 Camera/MainCamTrack 上（另有 MainCamTrack1），看向目标组 MainCamTargetGroup，取景用 CinemachineGroupComposer（DLL 里有 m_MinimumFOV、m_MaximumFOV、m_FOVAdder）。目标组的成员和权重就是上面那张表：自己权重 4 最大，落点 3，其他球员 2，球只有 1。也就是镜头主要跟自己和球的落点，不怎么跟球本身。落点成员的位置以 dropPosLerpSpeed 10 做平滑，相机沿轨道横移的速度是 mainCamHSpeed 6。

CameraValues 的 y / z 偏移上下限，[推测] 是相机或注视点随角色前后位置变化的偏移范围：Z 方向 ±3.5 m，Y 方向 −1.2 到 −0.1 m。

发球有两套虚拟相机：Camera/ServeCommonVCam（轨道 ServeCommonCamTrack 和 ServeCommonCamTrack1，目标组 CommonServeCamTargetGroup）和 Camera/ServePlayerVCam（轨道 ServePlayerCamTrack 和 ServePlayerCamTrack1）。处理类有 M2A5.Battle.BattleCamera 下的 ServeVCamHandler、MainVCamHandler、WatchVCamHandler（观战）。发球相机和主相机之间靠 Cinemachine 的 blend 切换，blend 时间在 prefab 里。

特写：Camera/CloseUpEffect/SmashFocusCam，只在星标扣球时用，参数见 §9.8。另有 CameraShake、FocusCameraEffect、CameraBlackDownEffect 三个效果类，以及调试用的 TopViewFullTestVCam、TopViewHalfTestVCam。

球的显示缩放 [配置事实] `text/SundryConfigs.txt` badmintonScal：maxHeight 4.0、minHeight 0.8、minScal 0.5、maxScal 0.28。球模型的显示大小随高度在 0.8 m 到 4.0 m 之间变化，哪个缩放值对应哪个高度没法从配置确定。

### 10.3 没找到的

## 11 给 Unity 复刻的建议

### 11.1 可以直接当初值的

| 项 | 数值 | 可信度 |
|---|---|---|
| 逻辑帧率 | 25 帧/s，击球那帧球已走约 0.07 s | 源码 + 回放 |
| 普通球形状 | 二次阻力抛体 k=0.24 /m、g=5.0 m/s² | 配置 + 回放，误差 2 cm |
| 过网规则 | 出球角按 5° 一档上调到网处 ≥ 157 cm | 回放 |
| 时间重映射 | first / lerp / last 三参数，§2.2 | 回放 |
| 21 条普通球路加发球两条的参数 | §3.1 的表 | 配置 |
| 扣杀 | 抛物线，a 上限 maxA×1e-6 /cm，网处压到 155 cm，匀速 velocity | 回放 |
| 落点表和公式 | §2.5 | 源码 + 回放 |
| 能量规则 | +20 / 0 / −40，上限 100，回合清零，40 和 100 两个档位阈值 | 回放（双打带技能样本） |
| 三圈半径 | 90 / 150 / 250 cm | 回放 |
| 移速 | 380 / 310 cm/s，无加速 | 配置 + 回放 |
| 动作时长 | §7.3 | 配置 |
| 相机震动、特写、压暗 | §9.8 | 配置 |
| 相机目标组权重 | §10.1 | 配置 |
| 击球提示 | 球高 ≤ 250 cm 且水平距离 ≤ 150 cm | 源码 |

实现上最省事的做法：把 `.ua/replica/tools/D_fy_curve.py` 的 `build()` 翻成 C#。输入曲线参数、起点高度、落点水平距离、网在路径上的比例、速度倍率，输出一张“真实时间 → (水平距离, 高度)”的点表，运行时按时间插值，水平方向沿起点到落点的直线走。

本作“三键 + 四档蓄力”和飞羽的对应建议 [推测]：
- 三个键的球族直接对应飞羽的近球、远球、高球三族。
- 蓄力档位对应飞羽的能量档。飞羽只有三档，可以把四档蓄力映射成 first / last 在 _0 和 _2 之间插值。例如近球内圈：first 14→9、last 17→13；远球内圈：first 12→10、last 24→16、lerp 70→44，出球角在第二档起从 5° 变 0°。
- 如果想保留“满档时远球被压平”的感觉，只在平远族做角度变化就够了，近球和高球只改时间参数。

### 11.2 要靠视频测量补的

| 项 | 为什么 |
|---|---|
| 相机位置、高度、俯角、FOV、跟随阻尼、发球到对打的 blend 时间 | 全在 prefab |
| 普通跳扣的起跳高度和滞空 | 逻辑位移在缺失的动作脚本里 |
| 跨步、鱼跃的精确位移曲线 | 同上；回放只能给量级（鱼跃约 230 cm / 4 帧） |
| 各动作的高度、距离判定范围的精确边界 | 同上；§6.1 的阈值是统计出来的，边界有 ±10 cm 的重叠 |
| 单打下的能量规则是否相同 | 回放全是双打 |
| 所有特效的时间轴、粒子数量、颜色 | prefab 缺失；只有贴图形态和少数配置参数 |
| 能量条的动效（涨、掉、满档火焰） | 只有精灵和材质名 |
| 击球停顿（hit stop） | 普通击球没有配置任何停顿或震动；是否有表现层的微停顿需看视频 |
| 球模型随高度的缩放方向 | 配置有四个数但对不上号 |

### 11.3 提醒

- 飞羽的“出手很冲、末段飘”有一半来自时间重映射，不是纯物理。如果本作想用自己的物理模型，至少要复刻“前段快放、过顶点后慢放”这个节奏，否则球速观感对不上。
- 飞羽的过网修正保证了普通击球永远不下网，失误只来自够不着、打到人、对手打死。这是一个很强的设计取舍，本作要不要跟需要单独决定。
- 圈层对球本身的影响很小，代价主要是后摇锁定（2 / 10 / 19 帧）和能量。复刻手感时后摇锁定比球路差异更重要。
